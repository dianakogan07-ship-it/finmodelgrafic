# ТЗ для Claude Code: СУЗ, итерация 1 — «Проект в рынке» (левый блок + графики)

Исходники: скриншоты текущего сайта `suz-dev.inlinegroup-c.ru/monitor/1`, финмодель `09_09_26 - 2026_08_03 ….xlsx`, кликабельный прототип (HTML, приложен отдельно — использовать как референс UI и поведения).

## 1. Цель итерации

Воспроизвести экран «СОКОЛЬНИКИ 09 09 NEW FM В РЫНКЕ»:

1. Левый блок: ползунки «Цена 1 м²» (шаг ±10 тыс. руб.) и «Темп продаж» (шаг ±100 м²), кнопка сброса, карточки «Финансовый результат» и «LLCR».
2. Графики по кварталам (цена и темп): наш проект + конкуренты, окно 4 квартала, переключение очередей, навигация по кварталам.
3. Данные нашего проекта берутся из xlsx-модели, ФР и LLCR пересчитываются моделью при изменении ползунков.

Вне итерации: вкладка «Рынок», разделы «Учетные записи», «Проекты конкурентов», «Внутренние объекты», виртуальный помощник, уведомления. Экран «Мониторинг» (круг объектов) и вход — минимально, как навигация к дашборду.

## 2. Что уже выяснено по файлу модели

| Что | Где | Значение в файле | Комментарий |
|---|---|---|---|
| Финансовый результат | `Dashboard_2!G69` | 18 575 830 372 руб. | формула `=G31-G37`; на экране показывать в млрд, 1 знак (18.6) |
| LLCR | `Dashboard_2!E81` | 1.199 | формула `=DashB_1_ЖК!D21`; 2 знака (1.20) |
| Подписи кварталов | `Продажи!2:2` с колонки `P` | «4кв. 24» … | U2 = «1кв. 26», W2 = «3кв. 26» |
| Цена 1 м², очередь 1 | `Продажи!U12` → вправо | руб./м² | **значения, не формулы** (ручной ввод). W12 = 572 692 → 573 на экране |
| Продано м², очередь 1 | `Продажи!U15` → вправо | м² за квартал | **значения**. W15 = 1 900 → «1.900» на экране (это 1 900 м², а не тыс. м²) |
| Итог площади очереди 1 | `Продажи!N15` | 53 395,77 м² | `=SUM(P15:BZ15)*B15` |
| Очередь 2 (квартиры) | `Продажи!58` цена, `61` продано | с Z (2кв. 27) | |
| Очередь 3 (квартиры) | `Продажи!104` цена, `107` продано | с AE (3кв. 28) | |
| Очередь 4 | `Продажи!150/153` | МФК (офисы) | в дашборд не выводим (уточнить) |

Правило поиска строк (не хардкодить): на листе «Продажи» строка, где `C` = номер очереди, `E` = «Квартиры», `D` = «Цена продажи с индексацией» / «Продано». Для очереди 1 это ровно U12/U15 — проверять и логировать расхождение.

Выручка по кварталу = цена × продано (`Продажи!14 = 12 × 15`), дальше модель считает всё остальное.

**Конкурентов в файле нет.** Их цены и темпы — из БД сайта (раздел «Проекты конкурентов»). Для итерации 1 — сид-таблица/JSON `competitor_quarter(project, color, quarter, price_k_rub_m2, pace_k_m2)`, выгрузить с текущего сайта.

## 3. Главный технический риск — пересчёт модели

Книга ~8 МБ, 50+ листов, **циклические ссылки с итеративным расчётом** (`<calcPr iterate="1">`). Проверено в LibreOffice headless:

- загрузка книги ~2 минуты;
- полный пересчёт (`calculateAll`) с включёнными итерациями — цикл сваливается в ошибки (`#NAME?`/`Err:502` по листам «1»–«4», «Summary», «Финансирование»), G69 = 0;
- инкрементальный пересчёт без итераций — выручка (`Продажи!W14`) меняется, а G69/E81 нет (цикл не пересчитывается).

Вывод: LibreOffice для этой модели не подходит без правки самой модели. Нужен движок, который считает как Excel.

**Решение (сделать спайк первым шагом, 1–2 дня):**

- **Вариант A (рекомендую).** Отдельный calc-сервис на Windows + Excel через `xlwings`/COM. Книга держится открытой, на запрос: записать входы → `Application.Calculate` → прочитать G69/E81 → откатить входы. Результат 1:1 с Excel. Пул из N процессов Excel под параллельных пользователей, очередь запросов.
- **Вариант B.** Aspose.Cells (коммерческий, поддерживает итеративный расчёт) на Linux. Принимать только если на эталонных сценариях совпадает с Excel.
- **Fallback.** Предрасчёт сетки чувствительности макросом в Excel (цена × темп для текущего квартала) и интерполяция на сервере. Быстро для пользователя, но жёстко ограничивает сценарии.
- `pycel` / `formulas` / HyperFormula — не брать без отдельного спайка (циклы + объём).

Критерий спайка: на 5 эталонных сценариях (снять вручную в Excel, см. раздел 9) G69 и E81 совпадают до 0,01 млрд / 0,005; время пересчёта ≤ 5 с.

Важно для UX: ряды цены и темпа — это входы, поэтому **графики обновляются мгновенно на клиенте**, пересчёт нужен только для ФР и LLCR (debounce 400 мс, индикатор «пересчёт…», отмена устаревших запросов).

## 4. Стек и структура

- Frontend: React + TypeScript + Vite. Графики — собственный SVG-компонент (сегментированные столбцы) или ECharts `pictorialBar`.
- Backend: Python 3.11 + FastAPI. Чтение модели — `openpyxl` (data_only) для начальных рядов и кэш-значений.
- Calc-worker: отдельный сервис по результату спайка (A или B), REST.
- БД: PostgreSQL (пользователи, проекты, конкуренты, версии моделей, сохранённые сценарии).
- Docker Compose для всего, кроме Windows-воркера (если вариант A).

```
/frontend        # React
/backend
  app/api/       # FastAPI роутеры
  app/model/     # парсинг xlsx, маппинг ячеек (config), сценарии
  app/calc/      # клиент calc-воркера
  tests/golden/  # эталонные сценарии
/calc-worker     # xlwings (Windows) или Aspose
/config/cell_map.yaml
```

`cell_map.yaml` — все адреса ячеек и правила поиска строк, чтобы новая версия модели не требовала правки кода.

## 5. Функциональные требования

### 5.1 Левый блок

- «Цена 1 м², тыс.руб.»: значение, ползунок, кнопки −/+ с шагом 10. Диапазон: ±30% от значения модели в якорном квартале, кратно 10.
- «Темп продаж, м²/кв.»: значение с разделителем разрядов («1 900»), шаг 100. Диапазон: 0 … остаток нераспроданной площади очереди.
- Под каждым ползунком мелко: квартал и ячейка (например «III кв. 26 · Продажи!W12»).
- Сброс ↻ возвращает все очереди к значениям модели.
- «Финансовый результат, млрд руб.» и «LLCR» — из пересчёта; рядом дельта к базовой модели (зелёная/красная).
- Для «Весь проект» ползунки неактивны, показывают агрегат.

**Семантика ползунков (предложение, согласовать с заказчиком):**

- Якорный квартал = первый видимый квартал окна, в котором очередь в продаже. По умолчанию окно начинается с текущего календарного квартала (сейчас III кв. 26 — совпадает со скриншотом: 573 / 1 900).
- Цена: новое значение в якорном квартале, все последующие кварталы очереди умножаются на тот же коэффициент (кривая индексации сохраняется).
- Темп: новое значение в якорном квартале, последующие кварталы масштабируются пропорционально так, чтобы итог площади очереди (N15) не изменился. Иначе модель ломает свои проверки площади (`DashB_1_ЖК!C4:C6`).

### 5.2 Графики (вкладка «Конкуренты»)

- Два ряда: «Цена 1 м², тыс.руб.» и «Темп продаж, тыс.м²»; 4 квартала в окне; подпись квартала «III кв. 26».
- В каждом квартале столбцы всех включённых проектов, отсортированы по возрастанию. Наш проект — белый, конкуренты — цвет своего чипа.
- Столбцы сегментированные (блоки с зазором), единая шкала Y для 4 видимых кварталов, от нуля.
- Подписи под столбцами только у минимума, нашего проекта (жирным) и максимума.
- Если значение нашего проекта изменено ползунком — пунктирная отметка базового значения модели.
- Тултип: проект и значение.
- Нет данных у проекта в квартале — столбец не рисуется.

### 5.3 Проекты (чипы)

Чип нашего проекта неактивен. Чипы конкурентов: «−» исключить с графиков, «+» вернуть (по умолчанию AHEAD выключен). Состояние хранится в сценарии пользователя.

### 5.4 Очереди и навигация

- Переключатель «Очередь: 1 · 2 · 3 · Весь проект» (кнопки строятся по данным модели). «Весь проект»: цена — средневзвешенная по проданной площади, темп — сумма.
- «Предыдущий / Следующий квартал» сдвигают окно на 1; «|‹» / «›|» — в начало / конец. Диапазон — от первого до последнего квартала продаж по данным модели.

### 5.5 Загрузка модели

Админ загружает новую версию xlsx → парсинг рядов и кэш-значений → валидация по `cell_map` (листы есть, строки найдены, итоги сходятся) → новая версия становится активной. Ошибки валидации показываются текстом с адресом ячейки.

## 6. API (черновик)

```
POST /api/auth/login                        {login, password} → JWT
GET  /api/objects                           список объектов для «Мониторинга»
GET  /api/projects/{id}/model               {labels[], cols[], queues:{1:{price[],area[],total}}, fr, llcr, model_version}
GET  /api/projects/{id}/competitors?from&to [{id,name,color,enabled_default,series:[{quarter,price,pace}]}]
POST /api/projects/{id}/recalc              {model_version, queues:{1:{price[],area[]}}} → {fr, llcr, calc_ms}
POST /api/projects/{id}/model               multipart xlsx (админ) → {model_version, warnings[]}
```

Сервер сам переводит ряды в адреса ячеек через `cell_map`; клиент адресов не знает.

## 7. Нефункциональные требования

- Графики реагируют на ползунок без задержки (< 50 мс); ФР/LLCR — ≤ 5 с после остановки ползунка.
- Пересчёт изолирован: входы пишутся в копию/сессию книги, после расчёта откатываются; параллельные пользователи не видят чужих сценариев.
- Логины, пароли и ключи — только в `.env`, не в репозитории.
- Тёмная тема, как на скриншотах; адаптив до 400 px (графики — горизонтальный скролл).

## 9. Критерии приёмки (файл 09_09_26)

- Открытие дашборда: окно III кв. 26 – II кв. 27, очередь 1; цена 573, темп 1 900; ФР 18.6; LLCR 1.20.
- Графики нашего проекта, очередь 1: цена 573 / 586 / 607 / 622; темп 1.9 / 2.4 / 2.0 / 2.6 (W–Z, строки 12 и 15).
- «+» у цены 3 раза → 603, столбцы цены нашего проекта с III кв. 26 выросли на 5,3%; «+» у темпа 5 раз → 2 400 м², сумма продаж очереди осталась 53 395,77 м².
- ФР и LLCR после изменения совпадают с Excel на эталонных сценариях (допуск 0,01 млрд / 0,005). Эталоны (снять вручную в Excel до начала разработки):
  1. W12 +10 000 руб.; 2. W12 −10 000; 3. W15 +100 м² с перераспределением хвоста; 4. X12 +10 000; 5. W12 +30 000 и W15 +500.
- Сброс возвращает исходные значения; переключение очереди, навигация и чипы работают без перезагрузки.
